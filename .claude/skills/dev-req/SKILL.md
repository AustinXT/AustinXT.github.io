# dev-req · manzi-blog 需求细化

**manzi-blog 适配入口**：先读项目 `CLAUDE.md`、`.42cog/` 四份、`state/board.md` 与 `state/memory/MEMORY.md`。
项目模板与领域约束统一在 [项目适配](../pr-ready/templates/manzi-blog.md)，基线和完整测试命令统一在
[项目配置](../pr-ready/references/project.config.json)。项目规约与本轮明确授权优先；迁入技能不扩大提交、推送、外发、合并或发布权限。

把粗略需求收敛为能执行、能验收的规格。纯 bug 或已有明确实现步骤的任务直接实现；纯研究按本项目四步研究技能推进，不强制走需求确认。

## 输入与探索

输入可为需求文本或当前项目 issue。CNB 用 cnb CLI（先看 issues 的实际帮助和参数）；GitHub 用 gh issue view 的 title／body／comments，仓库显式取项目配置。不要依赖未安装的 cnb-api，也不读取项目 .env* 或拼认证头。所有工具按 scripts/check-tools.sh 取用。
先用一句话说明理解；已有明确范围直接继续，只对实质歧义集中列出需人定的点。读现有代码、调用方、相关标准和同类文档；可按独立问题使用 Explore，当前宿主没有相应工具时直接检索，不把它作为前置阻塞。

## 实体建模

以 .42cog/cog.md 与当前实现为起点，列已有实体／新增实体／纯属性，记录拥有者、实际存放位置、字段类型、身份与关系、状态及默认值。用 Rust 类型、JSON／Markdown 合同或页面派生数据表示真实项目，不为文件／静态网站强造数据库表。
有状态流转则画状态机：列合法迁移、谁批准、哪些可选、失败回退、终态与重试；存储型实体才补键、唯一性、删除行为和迁移影响。

## 信息流

逐动作列触发、输入、输出、同步／异步、写入与外部副作用、失败清理、重试／幂等和进度反馈。领域示例只作形状参考：获选旧文指针 → 整理草稿／元数据 → 迁移台账 → 阅读页面与索引 → 本地导出检查 → 人审。
把 core／CLI／页面／导出／人工确认各自责任写清楚；只对本次范围内的动作设计，不补产品方向。

## 边界与元反思

逐项检查现有调用方与数据格式的兼容、重复和幂等、资源逃逸／超大输入／解析失败、并发或半写入、引用与生成物一致、原件和隐私边界。检查状态是否能卡死、缺哪些前提、同步异步是否符合任务、失败后用户能否恢复。
用独立视角审视并记录具体问题与修正，无需依赖深度思考 MCP。领域约束和实际验收由共用项目模板提供；没有证据的项标未验证，不为了通过规格省略需求。

## 输出与退出条件

输出含目标与范围、已有／新增实体、状态与信息流、受影响模块、兼容和权限边界、实现顺序及可观测验收点。UI、SQL、云服务按需求出现，不设为必填章节。
用 dev-docs 保存到现有 docs/plan/；尚待确认的分析写 _tmp/YYYYMMDD-issue-<N>/requirements.md。超过 300 token 的正文进文件，对话给路径与一句摘要。
有明确授权才将评论草稿发到 issue；纯文本需求也先本地交付，不默认输出长终端正文或替人外发。
验收：实现者能据实体与动作开工；每项需求有观察／测试方式；关键不确定项列为待拍板，已有授权不重复请求；人审／实效／发布分别标状态。
