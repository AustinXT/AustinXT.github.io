# dev-launch · Issue 发车

**manzi-blog 适配入口**：先读项目 `CLAUDE.md`、`.42cog/` 四份、`state/board.md` 与 `state/memory/MEMORY.md`。
项目模板与领域约束统一在 [项目适配](../pr-ready/templates/manzi-blog.md)，基线和完整测试命令统一在
[项目配置](../pr-ready/references/project.config.json)。项目规约与本轮明确授权优先；迁入技能不扩大提交、推送、外发、合并或发布权限。


**一句话**：给一条 issue，把状态校验、调研、分流、实现、验证、评审、交付串成自适应流水线——**确定性强的快走，不确定的先停下让人拍板**。

> **定位**：单条 issue、人在场时，直接把本技能当入口触发即可。**本技能只管一条 issue 从摄入到交付**——批量与无人值守的调度（预算/暂停/持久化）不在范围内。

## 0. 入口与前提

- **输入**：一个 issue URL，可附截图/报错/复现路径/历史引用/排除项。
- **默认策略**：**高不确定性先停、确定后放手**。
- **不替人做产品方向决策**。触及产品取舍必问。
- **加载项目模版**：方法论项目无关；项目专属部分（形态分类 / 交付分流 / 外部约束核对 / MEMORY 触发表 / issue 仓）外置到 `../pr-ready/templates/manzi-blog.md`，无匹配则读项目开工协议（AGENTS.md，缺失时 CLAUDE.md）。

## 1. 开场状态校验（永远第一步）

防「拿过期基线当真相」。`<基线>` 优先使用本次显式配置，否则取相邻 pr-ready 的 project.config.json（`origin/dev`）；不从远端默认 main 推断本项目目标：

```bash
git fetch origin && git status && git log --oneline -5 <基线>
```

确认基线 fresh、无脏工作区。**有未知分支或未提交改动 → 先调查再动，不覆盖在途工作。**

## 2. 摄入与调研（先别写代码）

1. **读全文 + 关联**：body、评论、关联 issue、最近合并的 sibling PR（套其改造模板）
2. **根因诊断**：能代码确诊就确诊；跨层的先定位是哪层，**别猜**
3. **分类打标**：确诊度 · 改动归属 · 工作量粗估 · **是否已部分实现**（先 grep 核对再补差量）· ROI · 是否 >3 天
4. **外部约束核对**：配额规则 / 付费门 / provider 状态等当前真相源，别用旧假设
5. **调研产出写文件**（项目开工协议里约定的一次性/过程文件目录，本项目采用 `_tmp/YYYYMMDD-issue-<N>/triage.md`；没有约定就用 `_work/`），对话只给路径 + 摘要

## 3. 确定性分流闸门（核心，别一刀切）

| 情形 | 行为 |
|---|---|
| 高确定性（根因明确、范围清晰） | 一句话说明 → 范围已清晰则直接实现；需规格时进 §5 |
| 高不确定性（多根因 / 需设计 / 触产品方向） | §4 列关键决策 → **停等拍板** |
| 可能已部分实现 | 先核对已实现部分，只补差量 |
| 值不值得做存疑 | 给「做 / 不做 / 关闭」结论 + 理由，等拍板 |
| 估算 >3 天 | **拒绝无人值守**，先建议拆 sub-issue |

> **粒度铁律**：能一条 issue 完成就一条——工程量大 / 跨栈 / 多阶段**都不是拆多 issue 的理由**（会爆炸）；**但一 issue 内可拆多个小 PR**，各自绿、各自评审。

## 4. 关键决策 & 等拍板

把需人定的点**集中列出**，每个给推荐方案 + 主要 tradeoff。列完**停下**，不替人决定；拿不准的明说「需要你定」。

## 5. 细化 + 回填 issue

调 `dev-req`（外部依赖）把范围细化成结构化实现规格，并把结果**发到对应 issue 评论区**，不只留在对话里（远端写入须在本任务明确授权内，否则只产草稿）。

## 6. 实现 → 验证 → 评审

1. **实现**：使用 Claude Code，沿用当前主模型配置（不因为换评审而修改开发档位）；动手前对照 项目模板触发表 `cat` 相关 memory；**改一处必 grep 同源 sibling 防漂移**
2. **三层验证**（规则 · 判据 · 实效；项目开工协议有专门章节则以其为准，没有则按此执行）：
   - 规则层：本地跑项目既有检查脚本（lint / typecheck / build / 单测等），全部退出码 0
   - 判据层：对照 `specs/` 或技能内置判据的正负例走查，判「好坏」
   - 实效层：留给人做最终定标，AI 不能替代
   规则层不过 → 先补脚本/契约再修实现，不绕过；三层都过才算通过
3. **checkpoint**：三层绿就存档，防网关中断/token 超限把活儿清零
4. **简化检查**：有 `simplify` 就调用；否则检查死代码、重复与过度设计，并写出结果，不依赖未安装技能
5. **`pr-ready`**（外部依赖）：开 PR 前全套自审 + 正式 Codex/GLM 双谱系评审，PR description 贴 invariant audit 表
6. **同快照复用**（§7）：复用 pr-ready 的双谱系结果，不重复同轮评审；代码、基线或共同材料变更后在新快照上整组重跑，到无 P0/P1/P2

## 7. Codex/GLM 双谱系独立评审（硬纪律）

开发谱系是 Claude（Anthropic），评审只用 Codex（OpenAI）、GLM-5.3[1M]（智谱）两个不同模型谱系，每轮在同一冻结快照上并行审，没有单独终审轮。最终放行须同快照两路均有效；模型与 Harness 分开记录。
唯一配置与调用层在相邻技能 `../pr-ready/references/review.config.json` 和 `../pr-ready/scripts/run-review.mjs`。执行前读 `../pr-ready/references/review-protocol.md`；主会话及其子代理与开发同谱系，自审不能冒充独立评审。

两位评审使用新进程、同一改动快照及需求/验收/批准非目标/测试证据，不继承作者会话，不预先分享彼此结论。
提示词落文件，经 stdin；CLI 参数和路径独立传入，绝不插值进 shell。外发需授权和脱敏。
每路 CLI/协议失败最多重试一次；仍失败转人工，不以别的谱系替代必审成员。合法负面结论不能靠换模型绕过。
同快照两份结果都有效、无 P0/P1/P2 才放行；证据不足先补，修正后在新快照上整组重跑双谱系。交付前再次核对快照；单路诊断不能算正式通过。

## 8. 交付分流

| 形态 | 路径 |
|---|---|
| CLI / 二进制 | 三层绿 → 走下面「发版前查票」→ **等人发版** |
| 库 crate | 注意 SemVer 与开源边界 |
| webapp / service | 开 PR → 自审 → Codex/GLM 双谱系评审 → **人工合并，绝不自动 merge** |
| 关 issue | **先 POST 回复说明处理结果，再 PATCH `state=closed`**——回复这一步不可省 |

**发版前查票（CLI/二进制，无专用发版脚本时按此清单手动过）**：
- 版本号已按 SemVer 更新，且与 tag/manifest（`Cargo.toml`/`package.json` 等）一致
- CHANGELOG／changelog 等价物已补当次改动，含 breaking 变更文案
- 三层验证在干净工作区跑过一遍（不是只在开发分支缓存结果）
- **回滚干跑**：确认上一个可用版本/tag 仍可一键切回（如 `git tag` 存在、旧二进制/旧发布产物未被覆盖）
- 项目若已有专用发版脚本（如 `scripts/release.sh`），优先用脚本而非本清单；清单出的问题多了就该把它固化成脚本

> 库 crate / webapp 通用的「打分支绿灯」判据参考项目开工协议的验收/发布章节，没有就按上面清单类推。

## 9. 意外处理矩阵

| 意外 | 处理 |
|---|---|
| git 状态过期 / 未知分支 | §1 先 fetch + 调查，不覆盖在途工作 |
| 根因模糊 | 先定位层级再设计，不猜 |
| 外部约束已变 | 动手前核对当前真相源 |
| 估算 >3 天 | 拒绝无人值守，先拆 |
| sibling 漂移 | 改一处 grep 全同源 |
| 三层验证规则层不过（缺检查脚本/契约） | 先补齐脚本或契约——这是整改，不是绕过 |
| 项目旧 review.md 不存在 | 使用 `../pr-ready` 的唯一配置；不再逐项目问阵容 |
| 任一必审 Harness 不可用 | 有界重试后转人工，不降为单路，也不换同谱系模型补位 |
| 输出可能超长 | 写项目约定的过程文件目录（本项目是 `_tmp/`），对话给路径 + 摘要 |
| 触及产品方向 | 停下问人，不编造产品叙事关 issue |
| 单条卡住（无人值守） | 登记 follow-up，跳下一条；留 PR 不强合 |

## 10. MEMORY 关键词触发表

触到对应概念时**动手前** `cat` 对应 memory；**开 PR 前**在 description 贴 invariant audit 表。任何 commit/PR 前先看项目 PR 评审方法论 memory；任何 close issue 前看「先回复再关闭」纪律。
