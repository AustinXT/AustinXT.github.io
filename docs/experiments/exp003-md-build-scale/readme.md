# exp003：静态导出 × 文章数规模

日期：2026-10-10。服务的取舍：`../../research/005_md-rendering/decision.md`。

## 假设

候选 A（构建时把 MD 编译成 HTML，再静态导出）在 3000 篇规模下仍然可行，具体满足四条：

- 详情页的 HTML 与 JS 字节与篇数无关；
- 构建时间近似线性，3000 篇在 5 分钟内；
- 全量列表随篇数线性变重，分页页大小恒定；
- 正文在 HTML 和内嵌 RSC 数据里各一份。

## 做法

- 用 APFS 写时复制克隆 `src/site/`，当时放在 `_tmp/20261010-md-rendering/exp-scale/site`（2026-10-10 已删），所有改动只在克隆里做，改动的文件存在本目录 `clone-changes/`；未安装依赖、未联网、未动原工程。
- 合成正文用固定种子从常用汉字词表抽样，直接输出 HTML 片段，模拟「MD 已编译」的产物，所以**不含 Markdown 解析成本**。篇幅分布为 30% 约 2000 字、50% 约 5000 字、20% 约 15000 字。另有一篇固定的 8236 字文章，在各规模下内容完全相同，用于跨规模对比。
- 新增三个路由：详情 `[slug]`（Server Component，用 `dangerouslySetInnerHTML` 插入正文）、全量列表、每页 20 篇的分页目录。
- 规模取 N = 100、1000、3000、6000。
- 测量项：
  - 构建墙钟时间与内存；
  - 产物体积与文件数；
  - 页面原始字节，及 gzip 6、brotli 11、brotli 5 压缩后的字节；
  - 内嵌数据占比与重复代价；
  - 预取会取到的分段文件。

原始数字在 `results/results.md`（137 行），以及同目录的 `results.json` 和各规模的 `measure.json`、`build.log`；脚本在 `scripts/`。2026-10-10 负责人决定删除实验材料：克隆工程、合成正文与各次 `out/`、`.next/` 产物已删，只保留这些小文件；合成正文可用 `scripts/gen.py` 按固定种子重建。下面的关键数字我已从产物独立复测：详情页字节、全量列表与分页的 gzip、`out/` 文件数。

## 结论

| 指标 | N=100 | N=1000 | N=3000 | N=6000 |
|---|---|---|---|---|
| 构建墙钟（秒） | 3.99 | 7.63 | 12.38 | 43.30 ⚠ |
| 固定文章详情页 HTML（字节） | 65,760 | 65,760 | 65,760 | 65,760 |
| 详情页 JS（7 个文件，gzip 后） | 139,770 | 同左 | 同左 | 同左 |
| 全量列表页（gzip 后） | 9.3 KB | 61.1 KB | 167.6 KB | 319.4 KB |
| 分页第 1 页（gzip 后） | 4.2 KB | 4.2 KB | 4.2 KB | 4.1 KB |
| `out/` 体积 / 文件数 | 15.8 MB / 590 | 137 MB / 5,315 | 411 MB / 15,815 | 825 MB / 31,565 |

逐条看假设：

1. **详情页与篇数无关：成立。** HTML、JS 清单和 CSS 在四个规模下完全相同。
2. **构建时间：3000 篇以内成立。** 构建为固定开销加约每篇 2–4 ms。6000 篇时测得超线性（⚠），但当时机器有外部高负载，连与篇数无关的编译阶段都慢了 2.4 倍，不能下结论。
3. **列表：成立。** 全量列表每多一篇增加约 53 B（gzip）；分页页大小恒定。全量列表本身被预取时要取的那份数据，3000 篇时为 98 KB（gzip）。
4. **正文双份：成立，但代价取决于篇幅和压缩方式。**
   - 内嵌数据占详情页原始字节的 55%；`out/` 里每篇正文共存 5 份。
   - 重复部分的再付比例：brotli 下各种篇幅都只有 6–10%；gzip 下片段不超过 17 KB 时只有 8–14%，26 KB 时 76%，55 KB 时 98%。这与 gzip 只有 32 KB 回看窗口的机制一致。
5. **预取：** 目录里每条被预取的链接会取目标文章的分段文件。3000 篇里这类文件 gzip 后均值 11.2 KB、p90 22.9 KB，比一整页分页目录还大。

## 实际失败

- 第 1 次构建作废。克隆放在被忽略的 `_tmp/` 下，Tailwind v4 的自动源检测扫了 26,017 个文件（包括 `node_modules` 和正文），CSS 从 8.7 KB 膨胀到 79 KB。
- 在克隆里补 `.gitignore` 无效。最后在克隆的 `globals.css` 里改用 `source(none)` 加显式 `@source` 列表，才得到有效数据。
- **对真实工程的含义**：正文如果放在 `src/site/` 里，同样会被 Tailwind 当源码扫描，要显式排除。
- 构建额度用完，6000 篇没有在空闲机器上复跑。

## 时间与规模边界

- 实验在 Next 16.4.0、Node 26.10.0、10 核 16 GB 的本机上，机器有外部负载，绝对时间应视为偏上限。
- 合成正文比旧文长：旧文中日韩字符中位 1505 字；合成正文取前 100 篇，中位 5331 字，约为旧文的 3.5 倍。按真实篇幅，`out/` 体积会更小。
- **gzip 的重复代价不能按篇幅外推。** 实验页面的外壳极简，正文的两份离得近。真实页面外壳更大时，两份会被推远：参照站一篇 5343 字的文章，两份相距至少 36.7 KB，超过 32 KB 窗口，gzip 下重复部分再付 92%（`../../research/005_md-rendering/evidence/probe-result.txt:146-148`）。另外，本实验最短的那篇（1814 字），内嵌数据整体也让页面重 46–48%，gzip 和 brotli 都一样（`results/extra_lengths_N3000.json`）。
- **未测**：
  - remark/rehype、代码高亮、公式等真实 MD 插件的构建成本；仅有 Python-Markdown 的旁证，约 2.3 ms/篇，不代表 remark；
  - 浏览器里实际的预取次数、水合、手机 LCP/INP；
  - 增量构建；
  - 托管平台的体积上限与 brotli 支持；
  - 正文用 React 元素树而非 HTML 字符串时的体积差。

## 追加实验：Route Handler 直出纯 HTML（A2-R）

对抗审查指出漏了一个候选：用静态导出支持的 Route Handler 直接输出纯 HTML 文章页。于是在同一个克隆里补做一次，最多两次构建，N=100（实际 99 篇）。`lib/exp-content.ts` 加了 `EXP_N` 来限定规模。构建日志在 `results/routehandler-build*.log`。

- **P1 模板字符串直出：可行。** 路由写在 `app/plain/[slug]/index.html/route.ts`，用 `force-static` 加 `generateStaticParams`，100 篇规模构建 3.26 s。产物与普通页面路由对比如下，正文逐字节相同：

  | 同一篇 8236 字文章 | 原始 | gzip | brotli | `<script>` 数 | 每篇文件数 |
  |---|---|---|---|---|---|
  | 普通页面路由（A2） | 65,760 B | 25,258 B | 14,148 B | 18 | 5 |
  | Route Handler 直出（A2-R） | 26,806 B | 12,079 B | 10,889 B | 0 | 1 |

- **P2 用 `react-dom/server` 复用共享布局：失败。** Turbopack 构建直接报错：「You're importing a component that imports react-dom/server」。也就是说，A2-R 不能复用现有的 React 组件，导航和布局只能另写模板。失败的路由文件保存在 `clone-changes/p2-failed/`。
- **未验证**：
  - 托管上 `/plain/<slug>/` 能否正确返回 `index.html`，以及 Content-Type 是否正确；
  - CSS 的稳定引用；
  - 与普通页面之间的客户端导航；
  - 真机加载效果。
